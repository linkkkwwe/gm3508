## 21:40 串口缓冲：我改了 1 处，并推翻了自己的根因判断

用户现象："要把主的那个插拔一下，串口才有用"，要求软件自动处理。

### 我的第一判断（已被仿真推翻，勿复用）
以为 rx 缓冲被噪声填满后 `rx_len` 永久卡 23 → 主控回来的帧被整帧丢弃 → 必须拔插。
**错**：因为帧尾 `\r\n` 会触发 `handle_line()` 清空缓冲，缓冲能自愈。

### 时序仿真结论（115200，11.52 字节/ms，掉线 1s 灌满噪声 + 恢复后每 100ms 发帧）
| 策略 | 干净链路 | 掉线后恢复 |
|---|---|---|
| 旧逻辑（原样） | 20/20 | **9/10** |
| 缓冲回卷 | 20/20 | 9/10 |
| 回卷 + 每 1ms 清缓冲 | **0/20** | 0/10 |
| 回卷 + 掉线瞬间清一次 | 20/20 | 9/10 |

**关键**：旧逻辑本来就只丢 1 帧 → **缓冲不是"必须插拔"的根因**。
而且"每 1ms 清缓冲"是灾难：主循环 1ms 清一次会把正在接收的帧拦腰截断
（9 字节 @115200 要 0.78ms），即使链路干净也 0 帧。这条千万别加。

### 最终改动（仅 1 处，rail_control.c:153-169）
缓冲满时回卷覆盖，而不是永久丢弃新字节。纯健壮性改进，对症状无改善。
撤销记录：曾加过"链路超时时清缓冲"，已删除（仿真证明有害）。

### 仍未定位的根因
"必须插拔"不是缓冲问题。待用户实测：
- 掉线期间 `g_dbg_rc_bytes` 还涨不涨 → 判定线上有无噪声
- 用户拔插的到底是主控电源 / 串口线 / 主控板，含义完全不同
- 若掉线后 bytes 完全不涨且恢复后也不涨 → USART 接收真死了，看 ORE 与
  `HAL_UART_ErrorCallback`（main.c:253 已有恢复逻辑）

# 2026-10-16

## 现象：跑一段时间后"像掉线"，遥控指示灯仍显示连着，必须拔插/复位才恢复

链路：板A（遥控/蓝牙，USART 发 `$B,<sw>,<stick>,<en>\r\n`）→ USART1 RX(PB7) → rail_control → target
→ Motor PID → CAN1(PD0/PD1) → C620/M3508。用户看到"灯还连着"只能证明**板A 侧的无线链路**没断，
板B 内部的三层（USART 接收 / CAN 总线 / 状态机）任一层卡死，指示灯都照样亮。

## 查出的结构性缺陷（任一条都会造成"不可自愈"）

1. **CAN 总线关闭(bus-off)无自恢复** —— `can.c:48` `AutoBusOff = DISABLE`，
   且整个 application/ 里**没有任何** `HAL_CAN_ErrorCallback`（全仓库只有 Drivers 里的 weak 定义）。
   → 一旦 TEC 累计到 256 进入 bus-off，CAN1 收发同时停止且永远不会自己回来。
   → `CAN_motor_feedback_ready()` 恒为 0 → `main.c:142` 死循环发 0 电流 + 反复 reset。
   为什么"跑一段时间才掉"：本工程 trajectory 是 ±720°/2000ms，PID 长期把电流打满 16384，
   大电流导致地线噪声/EMI 上升、CAN 误码→TEC 累加，几十秒到几分钟才会到 bus-off 阈值。
2. **CAN 滤波器全放行** —— `can_comm.c:21-24` FilterId/Mask 高半都为 0，只校验 IDE/RTR，
   总线上任何节点的任何标准数据帧都进 FIFO0。多节点时会灌爆 FIFO0（FOVR 无处理）。
3. **反馈断 >100ms 会把整个 rail 状态机推倒重来** —— `main.c:149` 调 `rail_control_init()`，
   清 `frame_received`/`rx_len`/`line_ready`，mode 回 SAFE；`motor_ctrl_clear()` 还把
   `initialized` 置 0，**下一帧会以当时位置重新当 0° 参考点** → 每次 CAN 抖动，坐标系原点就漂一次。
4. `AutoRetransmission = DISABLE`（`can.c:50`，即 NART=1）：失败帧不重发，
   `HAL_CAN_AddTxMessage` 在 3 个邮箱满时返回 HAL_ERROR，代码**不检查返回值**。

## 定位方法（Keil Watch，一次定位在哪一层断）

| 观测量 | 含义 |
|---|---|
| `g_dbg_rc_bytes` | 还涨 = USART 接收活着，板A 在发字节；停了 = 板B 的 UART RX 死了（需要重新挂接收） |
| `g_dbg_rc_frames` | bytes 涨但 frames 不涨 = 帧格式错/被 procedure 判非法 |
| `g_dbg_rc_mode` | 4=SAFE；0/1=波形；2=手动；3=归位 |
| `motor_measure[0].received` / `last_rx_tick` | received=1 但 `HAL_GetTick()-last_rx_tick` 一直 >100 = CAN 断了 |
| `hcan1.Instance->ESR` | bit15 BOFF=总线关闭、bit14 LEC、bits[23:16] REC、bits[31:24] TEC |
| `hcan1.Instance->TSR` | 邮箱是否全满 |

## 板A（Guide_rail，主机）发送侧查出的问题 —— 2026-10-16

**板A 的 CAN 配置反而是健康的**：`can.c:47-49` AutoBusOff=ENABLE、AutoWakeUp=ENABLE、
AutoRetransmission=ENABLE。对比板B(GUID_RAIL) 是 AutoBusOff=DISABLE + 无 ErrorCallback。
→ 若真是 CAN bus-off，问题在板B 侧，板A 能自愈。两板 CAN 引脚都是 PD0/PD1，很可能同一条总线。

**① 主要嫌疑：板A 把 SerialPlot 遥测和遥控帧混在同一条 USART1 上发**
- `main.c:412` `serialplot_output()` 走 huart1，每 10ms、约 17~20 字节
- `main.c:355` `bt_send_rc_frame()` 也走 huart1，每 40ms、14 字节
- 板B 的 `rail_control_rx_byte()` 在**中断**里进缓冲、`handle_line()` 在**主循环**（1ms）里处理；
  `line_ready` 置位期间**所有新字节直接丢弃**（`else if (!line_ready)` 分支）
- 115200 下 87µs/字节 → 从 line_ready 置位到主循环清掉，最长丢 ~11 字节
- 板A 主循环顺序是先 bt_send_rc_frame 后 serialplot_output，但两者周期 40/10ms 成整数倍，
  相位随主循环抖动缓慢漂移 → **偶尔**遥控帧紧跟遥测行的 `\n`，前 6 字节（`$B,3,`）被丢，
  缓冲只剩 `-1000,1` → parse_frame 失败 → 200ms 无合法帧 → SAFE。
  **这解释了"跑一阵子突然不行、指示灯还亮、拔插/复位又好"的间歇性特征。**
- 根治：板A 关掉 serialplot_output（或改 100ms 一次）；或板B 改成 line_ready 期间不丢字节（双行缓冲）

**② 板A 阻塞发送拉长控制周期**：serialplot ~1.7ms、RC 帧 ~1.2ms，把 1ms 主循环偶尔拉到 ~2.7ms

**③ 板A 的 CAN 滤波器 ID 全放行**（`can_comm.c:21-24` MaskIdHigh=0），与板B 同总线时
  会互相把对方的帧收进 FIFO0，中断量翻倍

**④ 板A 上电 rc_ctrl 全 0 → sw=0 → 板B 判非法丢帧 → SAFE**，属正确行为（没遥控器就不动）

**⑤ 帧格式核对无误**：板A 发 `$B,<sw=s[0]>,<stick=ch[2]±1000>,<en>\r\n`，
  板B parse_frame 要求 sw∈[1,3]、stick∈[-1000,1000]、en∈{0,1} —— 语义与范围都匹配。
